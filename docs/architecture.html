01

Five principles that decide everything

Every downstream design choice traces back to one of these. When a later decision is ambiguous, the tie-breaker is whichever option honors these best.

Truth

Trades are the ledger

The transaction stream is the only source of transaction truth. Holdings are a view of it.

Derived

P&L is computed

Never store hand-entered holdings. The engine derives positions, realized & unrealized P&L.

Authority

Ownership is server-side

The backend verifies a manager owns a client on every request. Path IDs are never trusted.

Idempotent

Uploads are versioned

Re-uploading a wider date range dedupes by fingerprint — P&L never doubles.

Enrichment

Market data only values

yfinance says what holdings are worth, never what a client owns. Outage ≠ empty portfolio.

Mongo-only trade-off

Integrity moves to the app

No FK / joins / schema from the DB — enforced in FastAPI via Pydantic, ownership guards & unique indexes.

02

System context

The browser is static and secret-free. It only ever talks to the API — never to Mongo or yfinance directly.

Super Admin ─┐
Manager     ─┼─▶ React SPA (GitHub Pages) ──HTTPS · JWT──▶ FastAPI (Azure Functions)
Client (P4) ─┘                                              │
                                                              ├─▶ MongoDB (Azure)
                                                              └─▶ Market Data Service ─▶ yfinance
                                                                                         (Kite later)

Why the split matters: provider keys, JWT secret and the Mongo URI live only in Azure Functions app settings. GitHub Pages knows nothing but the API base URL.

03

Backend components

Strict layering: routers → services → db. The engine is pure Python — no Mongo, no FastAPI — so it is unit-testable and reusable when Kite arrives.

FastAPI app
├── auth          login / refresh / logout · JWT issue + verify
├── rbac          role + ownership guards (injected dependency)
├── users         super-admin manages managers
├── clients       managers manage their own clients
├── tradebooks    upload → validate → import → version history
├── trades        query / filter the raw ledger
├── engine        FIFO positions + P&L  — pure, DB-agnostic

├── securities    security master: symbol → sector / asset class
├── market_data   MarketDataProvider ⇢ YFinanceProvider + cache

└── audit         append-only action log

05

Ingestion pipeline

The "I uploaded it twice" problem is solved structurally: exact files are blocked by hash, overlapping rows by a unique fingerprint index.

POST file ─▶ parse xlsx ─▶ map columns (zerodha profile) ─▶ validate rows ─▶ file_hash
                                                                          │
                     exact file exists? ─── reject 409 ◀────────────────────┘
                                                                          │
        insert upload(vN, PENDING) ─▶ build per-row fingerprint ─▶ insertMany(ordered:false)
                                                                          │
        overlapping rows fail dup-key → counted, not doubled ◀────────────┘
                                                                          │
                     update upload → IMPORTED / PARTIAL ─▶ trigger recompute

Column mapping is a named profile (zerodha.yaml), not hardcoded. A new broker is a new profile with zero engine changes. Zerodha's Trade ID becomes the strongest fingerprint component when present.

06

FIFO engine — worked example

Sells match against the oldest open buy lots. Charges fold into cost basis: buy = price·qty + charges, sell proceeds = price·qty − charges.

BUYINFY · 100 @ ₹1,400lot A
BUYINFY · 50 @ ₹1,450lot B
SELLINFY · 70 @ ₹1,550↳ 70 from lot A
OPEN30 @ ₹1,400  +  50 @ ₹1,450= 80 sh
Remaining position
80 shares
Realized
70 × (1550−1400)
Unrealized
qty × (LTP − avg_cost)

Total P&L = realized + unrealized · Return % = total ÷ invested.

The engine is pure. It takes an ordered list of trades and returns positions + realized P&L with no database access — the single most-tested unit in the system, and the reason a future Kite integration is a provider swap, not a rewrite.

09

What we explicitly won't do

Carried over from the prototype's mistakes — each is a decision, not an oversight.

✕In-memory storage as the store of record.
✕Analytics in the frontend — the engine owns P&L.
✕One giant server.js — layered services instead.
✕Storing only current holdings — keep the trade ledger.
✕Deleting previous uploads — version & dedupe.
✕Trusting client IDs from the frontend.
✕Hardcoded sector maps — use the security master.
✕Browser → yfinance directly, ever.
